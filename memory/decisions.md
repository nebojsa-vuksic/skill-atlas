# Decisions

## Kotlin on the JVM, with Clikt, not kotlinx-cli (2026-09-30)

The CLI is Kotlin 2.x targeting Java 21 and built with Gradle. Command-line parsing uses
`clikt-core`.

**Why:** the owner chose Kotlin. `kotlinx-cli` was last released at 0.3.6 and is effectively
abandoned. `clikt-core` avoids the Mordant dependency and lets us map every outcome to
the exit codes in spec section 7 ourselves.
**How to apply:** exit codes are decided only in `Main.kt` (`SkillAtlasCli`). New failures get
a `SkillAtlasException` subclass with an exit code in `Errors.kt`.

## Always scan the default branch, and never offer a ref option (2026-09-30)

`scan` has no `--ref`. The branch comes from the GitHub API's `default_branch`, which may
be `main` or `master`.

**Why:** the owner asked for "always master", and it turned out they meant the default
branch. Their own repo and `anthropics/skills` use `main`.
**How to apply:** don't reintroduce ref wording in the spec or the CLI.

## Clone only SKILL.md files (2026-09-30)

The clone is shallow and partial (`--filter=blob:none --no-checkout`), followed by a
sparse checkout of `SKILL.md`.

**Why:** a full checkout of JetBrains/kotlin took about 40 s and JetBrains/android about
78 s, which made the web view look stuck. Now they take about 8 s and 4 s.
**How to apply:** anything that needs more files than `SKILL.md` must widen the sparse
pattern on purpose. Fixture repos set `uploadpack.allowFilter`, so tests exercise this path.

## One core, three views (2026-09-30)

Scanning, the catalog, filtering (`SkillFilter`), and similarity (`SkillSimilarity`) are
shared by the plain and rich `scan` output, `browse`, and the web view.

**Why:** the owner asked for the web view's features in the terminal too, and keeping one
set of rules means the views can't disagree.
**How to apply:** the filter rules exist twice, in `SkillFilter.kt` and `web/app.js`.
`SkillFilterTest` expected values were generated by running `app.js` in Node, so change both
files together and regenerate those expectations.

## Rich output only in a terminal (2026-09-30)

The Mosaic views run only when stdout is a TTY. Piped output is plain text with no escape
codes.

**Why:** scripts and CI read stdout. This is detected with Mosaic's `Tty.isStdoutTty()`.
`browse` also needs stdin to be a terminal.
**How to apply:** never write escape codes in `TextReport`.

## Duplicate, product, and test-data skills (2026-09-30)

Byte-identical copies merge into one entry. The main path prefers agent folders
(`.agents` before `.claude`), then repository folders, then product folders. A copy under a
`resources` folder labels the entry *shipped in product*. Skills under a test folder or
`src/*test*` are ignored as fixtures. See spec section 4.4.

**Why:** these came from real repos. JetBrains/MPS has 114 files but 41 skills.
JetBrains/koog has jvmTest fixtures. JetBrains/android keeps skills in `agent/skills`.
**How to apply:** new edge cases get a fixture modeled on the real repo in
`EdgeCaseIntegrationTest`.

## Similar skills are TF-IDF cosine, with no AI (2026-09-30)

Weights: name 3, description 2, body 1 (the first 20,000 characters). Stopwords and short
words are dropped, and a trailing plural `s` is removed. Results are the top 5 at 0.05 or
more. See spec section 5.6.

**Why:** the brief said "a heuristic, no AI". It is deterministic and fast: about 115 ms
cold for 500 skills.
**How to apply:** the 500-skill timing test runs cold on 2-core CI runners. Keep that
margin. Fix slowness in the code, never by raising the 1 s limit.

## Markdown is rendered on the server and escaped (2026-09-30)

The web view gets `content_html` from commonmark-java, with `escapeHtml(true)` and
`sanitizeUrls(true)`, under a strict `default-src 'self'` CSP.

**Why:** skill files come from untrusted repositories. Rendering on the server with a
well-tested library beats a hand-written renderer in the browser.
**How to apply:** everything else goes into the page with `textContent` only. Browser tests
check that `<script>`, `<img onerror>`, and `javascript:` in a skill never run.

## Several repositories: one pass per repository, then one similarity pass (2026-09-30)

`scan` and `/api/scans` scan each repository on its own, up to 4 at a time, in URL order,
and never scan the same `owner/repo` twice. Similarity is then computed once over all of
them, with ids like `owner/repo:path`. `browse` and the shell stay single-repository.

**Why:** paths repeat across repositories, so ids must include the repository. Similar
skills in *other* repositories are the most useful part of scanning several at once.
**How to apply:** use `crossRepositorySimilarity`, not `SkillSimilarity.compute`, whenever
more than one repository is involved. Single-repository output must stay byte-identical,
because the old tests check it exactly.

## The web view caches scans for 10 minutes (2026-09-30)

`/api/scans` reuses a repository's result for 10 minutes (`ScanCache`), so adding or
removing a chip clones only new repositories. Cached results aren't logged again.

**Why:** without the cache, each chip change cloned everything again. Adding a 4th real
repository took 2.3 s with the cache.

## Demos are scripted and live on an orphan `demos` branch (2026-09-30)

Playwright video records the web view, and VHS records the terminal. `demo/record.sh` and
`demo/publish.sh` do the work, and the `record-demo` skill describes the process (spec
section 13).

**Why:** the owner suggested QuickTime, but it's manual, captures the whole screen, needs
permissions, and can't be repeated. `gh` can't upload attachments to PR bodies, and the
repository is private, so the files live on a branch and are linked with `?raw=true`.
**How to apply:** look at key frames with `ffmpeg -ss` before publishing. The first
multi-repo recording showed "0 of 63" for `repo:koog test`, a poor search to demo.

## The shell is a slash-command REPL on the same renderers (2026-09-30)

`skill-atlas` with no arguments in a terminal opens `shell` (spec 5.9). Commands print the
existing rich reports into scrollback, and the palette ranks exact, then prefix, then
substring matches. Pure classes hold the logic: `ShellCommands.kt` (registry, matching,
completion), `ShellState.kt` (history and keys), `ShellSession.kt` (commands) and
`ShellScreen.kt` (layout). `ShellView.kt` is the thin Mosaic layer.

**Why:** the owner asked for "a rich, interactive CLI … similar to the Claude CLI". Without
a terminal the old usage error stays, so scripts don't hang on a prompt.
**How to apply:** a new command is a row in `ShellCommands.ALL` plus a branch in
`ShellSession.execute`, with a unit test and a line in the spec's command table.

## Demo narration: an original voice, from local Kokoro (2026-09-30)

Demos have a voice-over and captions (spec 13.4). The voice is Kokoro (`kokoro-onnx`,
`af_heart`), a local neural TTS model. `demo/setup-voice.sh` installs it into `demo/.venv`
and `demo/.kokoro/`, both git-ignored.

**Why:** the owner asked for a celebrity's voice. We don't imitate real people, so it's an
original narrator instead. macOS `say` was "really robotic". The owner then chose Kokoro
over macOS Premium voices and cloud TTS, because it's natural, offline, and free.
**How to apply:** never clone or imitate a real person's voice. `DEMO_TTS=say` is only a
fallback.

## A narrated feature tour on the demos branch (2026-09-30)

Six demos (`demo/tour-*`) cover every feature. They're published to `demos/tour/` and
linked from the README (spec 13.5).

**How to apply:** when a feature changes what users see, update or add a tour demo, record
it again, and republish with `demo/publish.sh tour …`.
